Tổng Quan Kiến Trúc

SportShop được xây dựng trên mô hình kiến trúc Microservices phân tán, bao gồm một Client SPA ở Frontend kết nối thông qua API Gateway duy nhất. Mỗi Service sở hữu cơ sở dữ liệu riêng, hoạt động độc lập và đồng bộ thông tin lẫn nhau thông qua các cơ chế API đồng bộ hoặc Message Broker bất đồng bộ.

Công Nghệ Áp Dụng

Các công cụ và framework chính được áp dụng xuyên suốt hệ thống để đảm bảo bảo mật, hiệu năng và tính ổn định cao.

☕ Spring Boot 3.x
Core Backend Sử dụng Java 17 làm nền tảng phát triển các microservices độc lập, tích hợp các thư viện Spring Security, Spring JPA giúp triển khai nghiệp vụ nhanh chóng.
⚡ Spring Cloud Gateway
API Gateway Đóng vai trò cổng kiểm soát trung tâm, định tuyến API an toàn dựa trên đường dẫn cấu hình, tích hợp bộ xác thực mã token JWT và bộ giới hạn tần suất (Rate Limiter).
⚛️ React / Vite
Client SPA Ứng dụng Single Page Application xây dựng trên React, tích hợp Context API quản lý trạng thái giỏ hàng lai và Axios giao tiếp API qua Gateway.
💾 MySQL 8.0
Database Áp dụng mô hình Database-per-Service. Mỗi service sở hữu một schema MySQL riêng biệt (auth_db, product_db, order_db, payment_db, chat_db) để cô lập dữ liệu.
🔴 Redis Cache
Middleware Đảm nhiệm 3 vai trò quan trọng: Caching thông tin sản phẩm tránh quá tải DB, làm kho lưu metadata Rate Limit cho Gateway, và làm cơ chế Khóa phân tán (Distributed Lock) tại Payment.
🐇 RabbitMQ
Message Broker Hệ thống gửi tin nhắn bất đồng bộ, chịu trách nhiệm truyền tải các Event trạng thái (cập nhật tồn kho, thay đổi trạng thái đơn hàng, kích hoạt gửi mail) để giảm thiểu sự phụ thuộc trực tiếp.
🤖 Gemini AI & Rules
Integrations Động cơ chatbot tư vấn kích cỡ (size) và thông tin sản phẩm. Tích hợp bộ luật Rule-based xử lý nhanh tại chỗ và gọi API ngoài của Gemini khi gặp các câu hỏi nâng cao.
📧 SMTP Mail / JavaMail
Integrations Giao thức gửi mail tự động cho khách hàng. JavaMail Sender được tích hợp trong Notification Service để gửi thông báo xác nhận thanh toán/đơn hàng thành công qua Gmail.

1. Đăng Ký, Đăng Nhập & Bảo Mật Xác Thực JWT

Luồng bảo mật đăng nhập người dùng và cấp mã JWT để xác minh danh tính trên toàn hệ thống.

sequenceDiagram autonumber actor Guest as Khách hàng participant React as React Frontend participant Gateway as API Gateway (8080) participant Auth as AuthService (8081) participant DB as Auth DB (MySQL) Guest->>React: Nhập username, password & Đăng nhập React->>Gateway: POST /api/v1/auth/login Gateway->>Auth: Định tuyến yêu cầu Auth->>DB: Truy vấn User bằng Username DB-->>Auth: Trả về User (Mật khẩu băm BCrypt) Auth->>Auth: So khớp mật khẩu (BCrypt matches) alt Mật khẩu hợp lệ Auth->>Auth: Tạo JWT Token (HS256) Auth-->>React: Trả về JWT Token & Role info React->>React: Lưu JWT vào LocalStorage else Mật khẩu không hợp lệ Auth-->>React: Trả về HTTP 401 Unauthorized end
Bước 1

Gửi Yêu Cầu Đăng Nhập

Khách hàng nhập tên tài khoản và mật khẩu tại giao diện React. Frontend gửi yêu cầu POST đến /api/v1/auth/login đi qua API Gateway trung chuyển.

Bước 2

Xác Thực Tại AuthService

AuthService nhận yêu cầu, truy vấn bảng users trong auth_db để kiểm tra. Mật khẩu được mã hóa dạng băm BCrypt và so khớp qua hàm BCryptPasswordEncoder.matches().

📄 AuthService.java
Bước 3

Cấp Phát Mã JWT

Nếu thông tin hợp lệ, AuthService tạo một chuỗi mã hóa JWT Token (HS256) chứa thông tin người dùng và quyền truy cập (Role) với thời gian hết hạn là 24 giờ, trả về cho Frontend.

Bước 4

Định Tuyến & Phân Quyền Gateway

Frontend lưu JWT vào LocalStorage. Với mọi request API sau đó, Frontend đính kèm token trong Header Authorization: Bearer [JWT]. API Gateway sẽ tự động giải mã, kiểm tra chữ ký token và xác định quyền truy cập trước khi chuyển tiếp yêu cầu đến các microservices nội bộ.

📄 JwtAuthenticationFilter.java

2. Đồng Bộ Giỏ Hàng Persistent (Guest to Member Sync)

Quy trình quản lý giỏ hàng lai giữa bộ nhớ trình duyệt tạm thời và lưu trữ vĩnh viễn trong MySQL khi đăng nhập.

sequenceDiagram autonumber actor User as Khách hàng participant React as React Frontend participant Gateway as API Gateway (8080) participant Order as OrderService (8083) participant DB as Order DB (MySQL) Note over User, React: Trạng thái: Chưa Đăng Nhập (Guest) User->>React: Thêm sản phẩm A (size L) vào giỏ hàng React->>React: Lưu vào LocalStorage ['cart'] Note over User, React: Tiến hành Đăng Nhập User->>React: Đăng nhập thành công React->>Gateway: POST /api/v1/orders/cart/sync (Kèm localCart) Gateway->>Order: Định tuyến yêu cầu Order->>DB: Truy vấn giỏ hàng cũ của User Order->>Order: Merge gộp các sản phẩm local vào database Order->>DB: Lưu các bản ghi đã gộp vào bảng `cart_items` Order-->>React: Trả về danh sách giỏ hàng sau khi gộp React->>React: Gán danh sách mới vào State + Xóa LocalStorage ['cart']
Bước 1

Thao Tác Giỏ Hàng Khách Vãng Lai

Khi người dùng chưa đăng nhập, mọi thao tác Thêm/Sửa/Xóa sản phẩm trong giỏ hàng đều được lưu trữ trực tiếp tại bộ nhớ cục bộ LocalStorage của trình duyệt dưới dạng mảng JSON.

Bước 2

Gửi Sự Kiện Đồng Bộ Lúc Đăng Nhập

Ngay khi người dùng đăng nhập thành công, Frontend kích hoạt hàm đồng bộ giỏ hàng, gửi một request POST chứa toàn bộ danh sách sản phẩm từ LocalStorage lên API /api/v1/orders/cart/sync?username=[username] của Order Service.

⚛️ CartContext.jsx
Bước 3

Xử Lý Merge Dữ Liệu Tại Order Service

OrderService tiếp nhận danh sách sản phẩm. Nó truy vấn dữ liệu giỏ hàng hiện tại của người dùng trong bảng cart_items của order_db. Tiến hành gộp (Merge) thông minh: cộng dồn số lượng nếu trùng sản phẩm và phân loại kích cỡ (size), hoặc chèn bản ghi mới nếu sản phẩm chưa tồn tại.

📄 CartService.java
Bước 4

Lưu Trữ MySQL Vĩnh Viễn & Cập Nhật State

Sau khi gộp dữ liệu thành công, OrderService lưu các thay đổi mới vào MySQL. Trả kết quả giỏ hàng mới nhất về cho Client. Frontend nhận phản hồi, thay thế State giỏ hàng hiện tại bằng dữ liệu trả về và tiến hành xóa sạch LocalStorage để chuyển sang chế độ đồng bộ trực tiếp với cơ sở dữ liệu.

3. Đặt Hàng & Đồng Bộ Tồn Kho Bất Đồng Bộ qua RabbitMQ

Quy trình tạo đơn hàng và cập nhật số lượng tồn kho tự động giữa các microservices bằng Message Broker để tránh nghẽn luồng.

sequenceDiagram autonumber actor User as Khách hàng participant React as React Frontend participant Gateway as API Gateway (8080) participant Order as OrderService (8083) participant DB as Order DB (MySQL) participant Queue as RabbitMQ Broker (5672) participant Prod as ProductService (8082) participant Redis as Redis Cache User->>React: Nhập thông tin & Xác nhận thanh toán React->>Gateway: POST /api/v1/orders Gateway->>Order: Định tuyến yêu cầu Order->>DB: Lưu đơn hàng mới (Trạng thái: PENDING_PAYMENT) Order->>Queue: Publish StockUpdateEvent (Mã SP, số lượng) Order-->>React: Trả về đơn hàng vừa được tạo thành công Note over Queue, Prod: Xử lý bất đồng bộ Queue->>Prod: Consume StockUpdateEvent Prod->>Prod: Truy vấn MySQL & giảm số lượng tồn kho (stock) Prod->>Redis: Xóa Cache (Evict products, categories)
Bước 1

Khởi Tạo Đơn Hàng Mới

Khách hàng xác nhận đặt hàng tại trang Thanh toán. OrderService nhận thông tin giỏ hàng, tính toán tổng tiền, và ghi nhận đơn hàng mới vào bảng orders trong order_db dưới trạng thái PENDING_PAYMENT (Chờ thanh toán).

Bước 2

Bắn Sự Kiện Đồng Bộ Tồn Kho

Sau khi tạo đơn thành công, OrderService không gọi trực tiếp Product Service. Thay vào đó, nó bắn một thông tin sự kiện StockUpdateEvent chứa danh sách mã sản phẩm và số lượng mua vào Exchange x.product.exchange của RabbitMQ Broker.

📄 OrderService.java
Bước 3

Tiếp Nhận & Giảm Tồn Kho Tại Product Service

Hệ thống RabbitMQ phân phối tin nhắn đến queue q.product.stock-update. ProductService lắng nghe queue này, phân tích tin nhắn, truy vấn bảng products trong product_db và tiến hành giảm số lượng tồn kho (stock) đồng thời tăng số lượng đã bán (soldQuantity).

📄 ProductStockListener.java
Bước 4

Xóa Bộ Nhớ Cache Redis

Do số lượng sản phẩm và thông tin tồn kho thay đổi, ProductService lập tức kích hoạt xóa cache (Evict) các key Redis liên quan như products, products_by_category, product_details nhằm đảm bảo ở lần truy cập tiếp theo của khách hàng, dữ liệu hiển thị sẽ được nạp mới hoàn toàn từ MySQL.

4. Khóa Phân Tán Redis Chống Trùng Lặp & Cổng Thanh Toán MoMo

Cơ chế bảo vệ giao dịch thanh toán khi gặp tình trạng lag mạng, ngăn chặn người dùng bấm liên tục gây ra lỗi double-payment.

sequenceDiagram autonumber actor User as Khách hàng participant React as React Frontend participant Gateway as API Gateway (8080) participant Pay as PaymentService (8084) participant Redis as Redis Cache (6379) participant MoMo as MoMo Gateway (External) participant DB as Payment DB (MySQL) participant Queue as RabbitMQ Broker User->>React: Nhấn "Thanh toán qua MoMo" React->>Gateway: POST /api/v1/payments/create-payment Gateway->>Pay: Định tuyến yêu cầu Pay->>Redis: opsForValue().setIfAbsent(lockKey, "locked", 30s) alt Khóa chưa tồn tại (Thành công) Pay->>MoMo: Gọi MoMo API tạo URL thanh toán MoMo-->>Pay: Trả về link URL thanh toán Pay-->>React: Trả về URL thanh toán MoMo React->>User: Chuyển hướng sang giao diện MoMo else Khóa đã tồn tại (Thất bại) Pay-->>React: Trả về HTTP 400 Bad Request (Đơn hàng đang xử lý) end Note over User, Pay: Sau khi khách quét mã & thanh toán thành công MoMo->>Gateway: POST /api/v1/payments/momo-ipn (Callback kết quả) Gateway->>Pay: Định tuyến yêu cầu IPN Pay->>DB: Chèn lịch sử giao dịch thành công Pay->>Queue: Publish PaymentStatusEvent (Trạng thái: PAID) Pay->>Redis: Xóa khóa giải phóng (Delete lockKey)
Bước 1

Kích Hoạt Thanh Toán

Khách hàng nhấn nút "Thanh toán qua MoMo" tại trang hóa đơn. Yêu cầu tạo giao dịch thanh toán gửi đến API của PaymentService.

Bước 2

Thiết Lập Khóa Phân Tán Redis

Ngay khi nhận request, PaymentService kiểm tra sự tồn tại của khóa lock:payment:[orderId] trong bộ nhớ Redis thông qua lệnh redisTemplate.opsForValue().setIfAbsent(lockKey, "locked", 30, TimeUnit.SECONDS). Đây là cơ chế nguyên tử (Atomic operation).

📄 PaymentController.java
Bước 3

Xử Lý Khóa Trùng

If khóa đã tồn tại (nghĩa là đang có một giao dịch khác cho đơn hàng này đang xử lý song song), PaymentService trả về ngay lập tức mã lỗi HTTP 400 Bad Request kèm thông báo lỗi tránh trùng thanh toán. Nếu chưa tồn tại, khóa sẽ được thiết lập với thời gian sống tự động (TTL) là 30 giây.

Bước 4

Gọi Cổng MoMo & Giải Phóng Khóa

PaymentService thực hiện kết nối HTTPS POST gọi sang cổng thanh toán của MoMo API để lấy đường link thanh toán và trả về cho Client chuyển hướng. Sau khi hoàn tất giao dịch và nhận Callback từ MoMo, hoặc trong trường hợp kết nối lỗi xảy ra lập tức, khóa trên Redis sẽ được chủ động xóa bỏ để mở lại quyền giao dịch bình thường cho đơn hàng.

5. Chat Trợ Lý Ảo Thông Minh Bằng Rule-Based & Gemini AI

Quy trình xử lý hội thoại thông minh kết hợp giữa tốc độ phản hồi của luật tại chỗ và độ thông minh của LLM bên ngoài.

sequenceDiagram autonumber actor User as Khách hàng participant React as ChatWidget (Frontend) participant Gateway as API Gateway (8080) participant AI as AIService (8085) participant Gemini as Gemini AI API (Google) User->>React: Nhập câu hỏi và gửi ("Tư vấn size L") React->>Gateway: POST /api/v1/ai/chat Gateway->>AI: Định tuyến yêu cầu AI->>AI: So khớp qua Rule Engine cục bộ alt Khớp từ khóa rule (size, ship, payment, hello) AI-->>React: Trả về câu trả lời định sẵn (nhanh, miễn phí) else Không khớp luật AI->>Gemini: Gọi Gemini API với câu hỏi & context của shop Gemini-->>AI: Trả về câu trả lời sinh thông minh AI-->>React: Trả về kết quả cho ChatWidget end
Bước 1

Khách Hàng Hỏi Trợ Lý Ảo

Khách hàng mở khung ChatWidget ở góc trái màn hình, gửi các câu hỏi tư vấn về sản phẩm, cách chọn kích cỡ (size), chính sách thanh toán hoặc vận chuyển.

Bước 2

Kiểm Tra Luật Cục Bộ (Rule Engine)

Gateway chuyển tiếp yêu cầu đến AIService. Để giảm độ trễ và chi phí gọi API ngoài, service sẽ kiểm tra câu hỏi qua hàm getSmartFallbackResponse() để so khớp với các từ khóa phổ biến (size, ship, payment, hello) và trả lời ngay lập tức nếu khớp luật.

📄 AIController.java
Bước 3

Gọi API Gemini Làm Trợ Lý Dự Phòng

Nếu câu hỏi không nằm trong danh sách các luật có sẵn, AIService sẽ sử dụng Client API gọi sang hệ thống **Google Gemini AI API**, truyền câu hỏi kèm theo Context quy chuẩn của cửa hàng để AI tự phân tích và sinh câu trả lời thông minh.

Bước 4

Hiển Thị Kết Quả Lên Widget

Phản hồi trả về Frontend dưới dạng JSON. Giao diện ChatWidget nhận dữ liệu và kết xuất hiển thị sinh động, hỗ trợ định dạng Markdown nhẹ để trải nghiệm chat mượt mà, thân thiện.

6. Hỗ Trợ Khách Hàng Trực Tuyến Thời Gian Thực Qua WebSockets

Quy trình trao đổi tin nhắn trực tiếp giữa Khách hàng và Admin chăm sóc khách hàng thông qua kênh kết nối WebSocket liên tục.

sequenceDiagram autonumber actor User as Khách hàng participant React as ChatWidget (Frontend) participant Chat as ChatService (8086) participant DB as Chat DB (MySQL) participant Admin as Admin Portal (React) User->>Chat: Kết nối WebSocket (ws://localhost:8086/chat) Admin->>Chat: Kết nối WebSocket User->>Chat: Gửi tin nhắn qua Socket (JSON) Chat->>DB: Ghi nhận vào MySQL (chat_messages) Chat->>Admin: Forward chuyển tiếp tức thời tới phiên Admin Admin->>Chat: Admin phản hồi câu trả lời Chat->>DB: Ghi nhận câu trả lời vào MySQL Chat->>User: Forward chuyển tiếp câu trả lời về màn hình Khách

Thiết Lập Kênh Kết Nối WebSocket

Khi khách hàng nhấn nút liên hệ nhân viên hỗ trợ, trình duyệt khởi chạy kết nối hai chiều liên tục sử dụng giao thức WebSocket hướng tới cổng dịch vụ của Chat Service tại địa chỉ ws://localhost:8086/chat.

Bước 2

Nhận & Chuyển Tiếp Tin Nhắn Tức Thời

Tin nhắn được gửi qua khung chat dưới cấu trúc JSON. ChatService nhận tin, định dạng và định tuyến gửi trực tiếp đến phiên làm việc (Session) đang mở của nhân viên chăm sóc khách hàng (Admin) tại giao diện Admin Portal ngay lập tức.

📄 WebSocketConfig.java
Bước 3

Lưu Lịch Sử & Phản Hồi Từ Admin

Tin nhắn được lưu đồng thời vào bảng chat_messages của chat_db để làm căn cứ lưu trữ lịch sử. Admin nhập câu trả lời, gửi ngược lại qua kết nối socket về phía thiết bị của khách hàng, đảm bảo quá trình tư vấn diễn ra tức thì, không bị trễ trang.

7. Luồng Gửi Email Thông Báo Tự Động Qua Event-Driven & SMTP

Quy trình tự động phát hiện các giao dịch thành công và thực hiện gửi thư thông báo xác nhận cho khách hàng qua email.

sequenceDiagram autonumber participant Queue as RabbitMQ Broker (5672) participant Noti as NotificationService (8087) participant Auth as AuthService (8081) participant Order as OrderService (8083) participant SMTP as SMTP Mail Server (Gmail) actor User as Khách hàng Note over Queue, Noti: Nhận tin nhắn bất đồng bộ Queue->>Noti: Deliver PaymentStatusEvent (PAID) Noti->>Auth: HTTP GET /api/v1/auth/user (Lấy thông tin khách) Auth-->>Noti: Trả về email người dùng Noti->>Order: HTTP GET /api/v1/orders/{orderId} (Lấy giỏ hàng mua) Order-->>Noti: Trả về thông tin danh sách sản phẩm đơn hàng Noti->>Noti: Compile HTML Template động Noti->>SMTP: Gửi email qua JavaMailSender (cổng 587) SMTP-->>User: Gửi email hóa đơn xác nhận đơn hàng thành công
Bước 1

Phát Hành Sự Kiện Trạng Thế

Khi đơn hàng được thanh toán thành công, PaymentService phát hành sự kiện cập nhật trạng thái thanh toán lên RabbitMQ Exchange x.payment.exchange.

Bước 2

Tiếp Nhận Sự Kiện Tại Notification Service

NotificationService lắng nghe sự kiện trên thông qua queue liên kết q.payment.notification. Ngay khi nhận được tin nhắn sự kiện, service sẽ giải nén dữ liệu để lấy mã đơn hàng (orderId) và mã giao dịch liên quan.

📄 PaymentStatusListener.java
Bước 3

Thu Thập Dữ Liệu Phục Vụ Nội Dung Thư

Do kiến trúc cô lập dữ liệu DB, NotificationService sẽ thực hiện các cuộc gọi REST API nội bộ ngắn sang OrderService để lấy thông tin chi tiết đơn hàng (tên sản phẩm, số lượng, size) và sang AuthService để lấy email của người mua.

Soạn Nội Dung & Gửi Email Qua SMTP

Service tiến hành biên dịch nội dung thư dựa trên mẫu email động (HTML template). Dữ liệu sau đó được đẩy qua lớp thư viện JavaMailSender, kết nối trực tiếp đến cổng SMTP của Gmail (cổng 587) để thực hiện bắn email thông báo hóa đơn thành công trực tiếp đến hộp thư cá nhân của Khách hàng.
