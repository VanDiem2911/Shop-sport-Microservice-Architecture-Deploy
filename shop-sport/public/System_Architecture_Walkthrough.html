Database Per Service

Kiến Trúc Cơ Sở Dữ Liệu Phân Tán (Decentralized Databases)

Để đảm bảo tính độc lập hoàn toàn (Loose Coupling), mỗi microservice trong hệ thống SportShop quản lý một cơ sở dữ liệu MySQL riêng biệt. Dưới đây là cấu trúc chi tiết của từng database:

Tên Database Microservice Sở Hữu Các Bảng Thực Tế Mô Tả & Vai Trò
auth_db AuthService (Port 8081) users Lưu trữ tài khoản, mật khẩu đã mã hóa BCrypt, thông tin liên lạc và vai trò (ROLE_USER, ROLE_ADMIN).
product_db ProductService (Port 8082) categories, products, reviews Quản lý danh mục, thông tin chi tiết sản phẩm, số lượng tồn kho (stock), số lượng đã bán (soldQuantity) và đánh giá khách hàng.
order_db OrderService (Port 8083) orders, order_items, cart_items Lưu trữ đơn hàng, chi tiết sản phẩm trong đơn, và giỏ hàng vĩnh viễn (persistent cart) đồng bộ của từng khách hàng.
payment_db PaymentService (Port 8084) payments Ghi nhận lịch sử giao dịch thanh toán, số tiền, phương thức giao dịch và trạng thái thanh toán.
chat_db ChatService (Port 8086) chat_messages Lưu trữ lịch sử tin nhắn trò chuyện của khách hàng, bao gồm người gửi, người nhận, thời gian và Order ID liên quan.

Cơ Chế Đồng Bộ Hybrid (LocalStorage + MySQL)

Khi là khách vãng lai, giỏ hàng lưu ở LocalStorage. Ngay khi đăng nhập thành công, Frontend tự động gửi toàn bộ sản phẩm local lên API /sync. Backend sẽ gộp (merge) thông minh các sản phẩm này vào database MySQL của user đó và dọn dẹp LocalStorage để tránh trùng lặp.

Tự Động Tạo Bảng Qua Hibernate DDL

Nhờ cấu hình ddl-auto: update trong OrderService, bảng cart_items trong MySQL Database tự động được Hibernate sinh ra an toàn khi service khởi chạy mà không cần người dùng thao tác SQL thủ công.

Business Logic

Logic Trừ Kho & Tăng Lượt Mua

1. Giảm hàng tồn kho & tăng số lượng đã bán

Logic được xử lý an toàn tại backend của ProductService thông qua phương thức incrementSoldCount, đảm bảo hàng tồn kho (stock) không bao giờ bị âm:

product.setSoldQuantity(product.getSoldQuantity() + quantity);
int newStock = product.getStock() - quantity;
product.setStock(Math.max(newStock, 0));

2. Lưu địa chỉ và số điện thoại tự động

Khi khách hàng thanh toán thành công, hệ thống tự động gọi API cập nhật lại thông tin cá nhân của User dựa vào địa chỉ và SĐT mới nhất vừa điền.

3. Gợi ý sản phẩm bán chạy (Recommendation Sorting)

Tại trang danh sách sản phẩm (ProductList.jsx), sản phẩm được tự động sắp xếp theo lượt mua giảm dần (soldQuantity DESC), giúp đưa các sản phẩm phổ biến nhất lên đầu trang để kích thích mua sắm.

4. Xóa cache Redis tức thời để cập nhật kho

Khi lượt bán tăng và hàng tồn kho thay đổi, Product Service kích hoạt @CacheEvict để giải phóng bộ đệm Redis ngay lập tức, đảm bảo khách hàng sau vào xem sẽ nhận thông tin hàng tồn chính xác 100%.

Cơ Chế Caching Hiệu Năng Cao Với Redis

Khám phá cách Redis lưu đệm (Caching) dữ liệu sản phẩm để giảm tải cho MySQL và tăng tốc phản hồi dưới 2ms, cùng cơ chế dọn dẹp cache tự động.

Read Cache Flow

1. Quy Trình Đọc Dữ Liệu & Kiểm Tra Cache (Cache Read Flow)

Khi có yêu cầu lấy danh sách sản phẩm hoặc chi tiết sản phẩm, hệ thống sẽ ưu tiên tìm trong RAM của Redis. Nếu tìm thấy (Cache Hit), trả về ngay lập tức. Nếu không thấy (Cache Miss), truy vấn MySQL rồi ghi vào Redis để phục vụ lần sau:

sequenceDiagram autonumber actor Browser as Trình duyệt (Client) participant Gateway as API Gateway (8080) participant Product as ProductService (8082) participant Redis as Redis Cache (6379) participant DB as product_db (MySQL) Browser->>Gateway: GET /api/v1/products Gateway->>Product: Định tuyến đến getAllProducts() Product->>Redis: Kiểm tra Key "products::all" alt Cache HIT (Tìm thấy trong Redis) Redis-->>Product: Trả về dữ liệu JSON của các Sản phẩm Product-->>Browser: Trả về Client (Thời gian phản hồi < 2ms) else Cache MISS (Không tìm thấy trong Redis) Redis-->>Product: Trả về null Product->>DB: Query SELECT * FROM products DB-->>Product: Trả về List<Product> từ đĩa cứng Product->>Redis: SET Key "products::all" = List<Product> (Thời hạn: 1 tiếng) Product-->>Browser: Trả về Client (Thời gian phản hồi ~ 100ms - 200ms) end
Cache Eviction Flow

2. Quy Trình Đồng Bộ & Dọn Dẹp Cache Tự Động (Cache Eviction)

Để tránh tình trạng lệch dữ liệu giữa MySQL (DB thật) và Redis (RAM Cache), khi Admin thêm/sửa/xóa sản phẩm hoặc khi Khách đặt hàng làm thay đổi kho hàng, hệ thống tự động xóa bỏ (Evict) các cache cũ để buộc lần tải tiếp theo phải nạp lại dữ liệu mới nhất:

JPA Collection Fix

Khắc Phục Lỗi Tuần Tự Hóa JPA

Thách thức từ Hibernate PersistentBag

Trong thực thể Product, danh sách bình luận (reviews) được nạp chậm (Lazy Loading). Khi Jackson lưu danh sách này vào Redis, nó ghi nhận kiểu dữ liệu là PersistentBag (lớp con của List do Hibernate quản lý).

Nhận thấy Frontend lấy đánh giá qua một API riêng của Review Service chứ không lấy trực tiếp từ Product API, ta đính kèm @JsonIgnore lên trường reviews của class Product. Jackson sẽ bỏ qua hoàn toàn trường này, triệt tiêu 100% lỗi crash do deserialization ở lần F5 thứ 2!

Architecture Benefits

Ưu Điểm Vượt Trội Của Kiến Trúc Event-Driven

1. Loose Coupling (Tách biệt dịch vụ tuyệt đối)

OrderService hoàn toàn không cần biết địa chỉ IP, Port hay trạng thái hoạt động của ProductService. Giao tiếp qua Broker triệt tiêu mọi liên kết cứng (Tight Coupling).

2. Fault Tolerance (Khả năng chịu lỗi kháng sập)

Nếu server sản phẩm bị sập, người dùng vẫn mua hàng bình thường. RabbitMQ bảo lưu 100% sự kiện trong đĩa cứng của hàng đợi. Hệ thống hoàn toàn kháng lỗi đổ vỡ domino.

3. Performance & Thao tác tức thì

Giảm thiểu thời gian chờ đợi mạng qua REST API đồng bộ. Người dùng nhận thông báo mua hàng hoàn tất tức thì dưới 10ms.
